# バックアップとリカバリ

本章では、OQTOPUS Cloud が状態を持つデータを誤削除から保護する仕組みと、その復旧方法について解説します。保護は多層構成です。重要なリソースは誤って削除しにくくし（削除保護）、それでもデータが失われた場合には復元できるようにしています（バックアップ / バージョニング）。

## 保護対象

| リソース | 削除保護 | 復旧手段 |
| --- | --- | --- |
| Cognito ユーザープール（user / admin） | `prevent_destroy` + Cognito の削除保護 | S3 への日次エクスポート（`cognito-backup` モジュール） |
| RDS (MySQL) | `prevent_destroy` + RDS の `deletion_protection` | 自動スナップショット（5日保持） |
| RDS ストレージ暗号化 KMS キー | `prevent_destroy`、削除猶予30日、キーローテーション | その場で保護（下記の注記を参照） |
| S3（ジョブストレージ） | `prevent_destroy` | バージョニング（非現行バージョンを7日保持） |
| S3（ロギング） | `prevent_destroy` | ライフサイクルによる移行 / 失効 |

> [!NOTE]
> KMS キーはバックアップやエクスポートができないため、その場で保護します。RDS のストレージ（および全スナップショット）はこのキーで暗号化されているため、キーを削除すると稼働中のデータベース **および** 全スナップショットが永久に復元不能になります。削除猶予を30日にしているのは、誤ってキーの削除予約をしてしまっても気づいてキャンセルできる時間を確保するためです。

## 削除保護

状態を持つリソースには Terraform の `lifecycle { prevent_destroy = true }` を設定しており、これはブロックを明示的に外すまで **Terraform 経由の破棄**を防ぎます。ただし保護の範囲はリソースごとに異なります。

- **Cognito, RDS** — リソース側の削除保護フラグも併用しているため、AWS コンソール / API からの削除も防げます。
- **RDS ストレージ暗号化 KMS キー** — 即時削除はできません。AWS KMS はキー破棄前に常に7〜30日（デフォルト30日）の待機期間を強制するため、その間は削除をキャンセルできます。Terraform では30日の待機期間を設定しています。（すべての呼び出し元に対して30日を保証するには、別途 `kms:ScheduleKeyDeletion` に対するキーポリシー条件が必要です。）
- **S3 バケット** — `prevent_destroy` は Terraform 経路のみを保護します。コンソール / API からの削除は依然として可能なため、`terraform plan` の確認と通常の IAM 権限制御が実質的な防御になります。

保護されたリソースを意図的に削除する場合（例: 環境の廃止）:

1. `prevent_destroy` ブロックを削除（またはコメントアウト）し、Cognito / RDS では AWS 側の削除保護フラグを `false` にします。`terraform apply` を実行します。これは保護を解除するだけで、まだ何も削除しません。
2. 続けて破棄を実行し（2回目の `terraform apply` / `terraform destroy`）、プランに意図した削除**のみ**が含まれることを確認します。

> [!NOTE]
> AWS 側の削除保護の無効化と破棄を**1回の apply**で同時に行うと失敗します。保護がまだ有効な状態で削除 API が呼ばれるためです。保護解除を1回目の apply で行い、破棄は次の apply で実行してください。

> [!IMPORTANT]
> `apply` の前に必ず `terraform plan` の出力を確認してください。プランに想定外の削除（destroy）や再作成（replace）が含まれている場合は、いったん止めて原因を調査してください。

## バックアップ

### Cognito — 日次エクスポート

`cognito-backup` Terraform モジュールは、EventBridge のスケジュールで1日1回起動する Lambda を作成し、対象ユーザープールの全ユーザー・全グループを専用の非公開・暗号化された S3 バケットへ JSON（`{pool_id}/{timestamp}-{run_id}.json`）としてエクスポートします。プールごとに独立して処理するため、あるプールが失敗しても他はスキップされず、かつ失敗時は invocation 全体を失敗扱いにしてアラーム可能にしています。バックアップは `backup_retention_days`（デフォルト: 30日）保持されます。

> [!NOTE]
> Cognito はパスワードや MFA/TOTP シークレットを公開しません。そのため復旧時には、ユーザーの再インポート、パスワードの強制リセット、MFA 有効ユーザー（例: admin プール）による MFA デバイスの再登録、および各ユーザー名を **新しい** `sub` に対応付けて RDS の `users.cognito_id` を更新する作業が必要です（再インポートしたユーザーには新しい `sub` が割り当てられます）。また CSV インポートツールはアカウントの有効/無効状態を引き継がないため、無効化済み（`Enabled=false`）のユーザーはインポート後に再度無効化（`AdminDisableUser`）する必要があります。

### RDS — 自動スナップショット

RDS の自動バックアップを5日保持（`backup_retention_period`）で有効化しています。復元はスナップショットから新しいインスタンスを作成する形になり、復号にはストレージ暗号化 KMS キーが存在している必要があります。より長い復旧期間が必要な場合は `backup_retention_period` を延長します（スナップショットのストレージ費用が増加します）。

### S3 — バージョニング

ジョブストレージ用バケットでバージョニングを有効化しています。ライフサイクルルールにより、非現行になった（上書き・削除された）バージョンは7日後に失効します。これにより、誤った上書き・削除をその期間内なら復旧でき、かつストレージ量は上限内に収まります。バージョン数での上限ではなく時間ベースの失効を採用しているのは、削除したオブジェクトの実データが「最後に残る1バージョン」として永久に残り続けるのを防ぎ、7日後に確実に消えるようにするためです。（その後も削除マーカーが残る場合がありますが、課金対象はオブジェクトのキー名の長さ分のみで、ごく僅かです。）

## 復旧クイックリファレンス

> [!NOTE]
> ここに記載するのは概要であり、完全な手順書ではありません。UNCONFIRMED / 無効化ユーザーの扱い、`sub` の再マッピング、既存 RDS 行との整合など、完全な復旧手順は必要になる前に別途整備・リハーサルしておくべきです。

- **ジョブオブジェクトの誤上書き / 誤削除（7日以内）** — ジョブストレージ用バケットのバージョン履歴から直前のバージョンを復元します（S3 コンソール、または `aws s3api list-object-versions` / `get-object --version-id`）。
- **Cognito ユーザープールの破損 / ユーザー消失** — バックアップバケットから最新のエクスポートを取得し、上記の復旧時の注意点（再インポート、パスワードリセット、MFA 再登録、`sub` の再マッピング）に従います。
- **RDS のデータ消失** — 自動スナップショット（ポイントインタイムリカバリ）から復元し、アプリケーションの接続先を切り替えます。ストレージ KMS キーが健在であることを確認してください。

## 保持期間とコストのまとめ

| バックアップ | 保持期間 | コスト |
| --- | --- | --- |
| Cognito 日次エクスポート | 30日（設定可能） | ほぼゼロ（JSON 数MB/日） |
| S3 ジョブバケットのバージョニング | 非現行バージョンを7日 | 約7日分の上書き/削除オブジェクト量に上限 |
| RDS 自動スナップショット | 5日 | スナップショットのストレージ費用（DBサイズに比例） |
